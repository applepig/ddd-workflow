# ddd.spec2 — 規格制定（機械對帳版）

規格制定階段。根據需求（或 plan/research 的成果）撰寫正式的規格書。

與 `/ddd.spec` 的差異：Self-Review 的完整性檢查從回憶式改為四道**對既有 artifact 的機械程序**、User Review Gate 改為呈現四份可逐條核對的成品；使用者要求修改時改為增量 Self-Review（v1 為整套重跑）；模板另新增「執行授權」「Open Questions」兩段與自由變數標注。改版原理見「Self-Review A」開頭的原則說明。

<HARD-GATE>
嚴禁在 spec.md 獲使用者確認前撰寫任何實作程式碼。
嚴禁省略邊界案例——每份 spec 至少列出一種 Edge Case。
嚴禁引入 docs/TECHSTACK.md 以外的技術而不在 ADR 中說明。
嚴禁在未盤點既有可複用資產前定稿——每份 spec 必須含「既有資產盤點 / Reuse Map」，列出可複用的 utility / 元件 / 樣式 token / pattern，或註明已搜尋確認無，不得留空。
嚴禁以「self-review 通過」一句話帶過完整性檢查——四道完整性程序各自的成品（對帳表、對稱性矩陣、走查紀錄、作者假設清單）必須實際產出並呈現給使用者。
</HARD-GATE>

## Checklist

你必須為以下每個項目建立 task 並依序完成：

1. **準備工作** — 建立/切換 feature branch、確認文件包、讀取 plan.md 與專案脈絡
2. **探索現有 codebase 並盤點可複用資產** — 了解現有架構、pattern、相關模組；產出「既有資產盤點 / Reuse Map」
3. **需求分析** — 釐清 User Story、驗收條件、邊界案例
4. **撰寫 spec.md** — 按模板填寫
5. **Self-Review A：完整性四程序** — 來源側對帳、對稱性檢查、具體 trace 走查、規範句出處（見下方；產出對帳表、對稱性矩陣、走查紀錄與作者假設清單）
6. **Self-Review B：品質檢查** — 7 項檢查（見下方）
7. **使用者審閱** — 呈現 spec ＋ 四份完整性成品（對帳表、對稱性矩陣、走查紀錄、作者假設清單）、等待確認、根據回饋修改

## 設計指引

### 沿用現有 Pattern

探索 codebase 時，先了解現有結構再提案。Spec 中的設計應與既有 pattern 一致。如果現有 code 有問題會影響本次開發（例如檔案過大、職責不清、邊界模糊），將改善納入 spec 的一部分——但不做無關的重構。

### Design for Isolation

將系統拆成職責清晰的小單元，每個單元應：

- 有一個明確的用途
- 透過定義好的介面溝通
- 可以獨立理解和測試

檢驗標準：能否不讀內部實作就理解這個單元做什麼？能否改內部實作而不影響呼叫端？如果不行，邊界需要重新劃。

## 準備工作細節

- 建立並切換至 feature branch：`git checkout -b feat/<編號>-<名稱>`（若已有分支則切換過去）。**branch 名稱中的 `<編號>-<名稱>` 必須與文件包 `docs/<編號>-<名稱>/` 完全一致**——這是從程式碼追溯需求的唯一索引，命名不一致會切斷追溯鏈。
- 確認或建立 `docs/<編號>-<名稱>/` 資料夾
- 讀取現有的 plan.md、research.md（如果有的話）
- 讀取 `docs/PRD.md`、`docs/TECHSTACK.md` 了解專案脈絡

## spec.md 模板

## 目標

## 非目標
明確列出不在範圍內的事項。

（關鍵 AC 附具體範例值——輸入→輸出可枚舉的附小表，枚舉不了的寫成不變量。範例值經使用者確認即成為測試預期值的權威來源（oracle），開發階段 worker 不得自行另訂）
- [ ] 條件 1
  - 範例：`<輸入> → <輸出>`、`<邊界輸入> → <輸出>`
- [ ] 條件 2
- [ ] 條件 3

- `src/path/to/file.js` — 說明

（動工前盤點既有可複用結構，優先沿用而非新造）

| 既有資產 | 位置 | 本次如何沿用 |
|---|---|---|
| <utility / 元件 / 樣式 token / pattern> | `src/...` | <複用 / 擴充 / 為何不合用要新建> |

（使用者在討論中給出的 standing authorization——已預先核可、不需逐次再確認的動作：例如「real model smoke 可自由執行，成本已核可」「可自由重試 N 次」。沒有就整段拿掉。這裡有寫的授權，後續 /ddd.work 派工與任何 session 的 agent 都應直接引用，不再回頭詢問；沒寫的維持教義預設——涉及花費與風險承擔時先問。執行授權不得涵蓋底線第 3、4 條——commit 與破壞性／不可逆操作一律逐次確認，授權文字涉及這兩類時視為無效並回頭詢問。）

> 驗證：依專案性質選擇——測試指令、CLI 驗收步驟、或其他可重現方式

- [ ] Red → Green → Refactor

## Open Questions（選填）

- [ ] <問題描述>（來源：對帳表 #N）

> **ADR 寫作要點**：重點是記錄「為什麼選 A 而不選 B」——未來的維護者需要的是決策脈絡，而非單純的結論。替代方案不需要長篇大論，一兩句說明被排除的理由即可。

> **自由變數標注**：spec 內文中每一處「由實作自行決定」「schema 自由定義」「格式不限」都要附上出處標注——`（使用者已確認）`或`（作者假設）`。沉默的自由讀起來像被確認過的設計，實際上可能是遺漏的墓碑；標注讓兩者可區分。

## Self-Review A：完整性四程序

原則：**遺漏無法靠回憶抓到**。你是從壓縮過的心智模型寫 spec 的——對話裡被你壓縮掉的東西，回憶時同樣不會出現。所以完整性檢查的迭代對象必須是「還沒被壓縮的原料」：對話原文、spec 的結構性質、具體情境的資料流。四道程序都是機械檢查，都產出可見成品，沒有一道依賴「想想有沒有漏」。

### 程序一：來源側對帳（對話 → spec，不是 spec → 對話）

逐則重讀使用者在本次對話（含 chain 進來的 /ddd.plan 討論）的**每一句發言**——從第一則開始實際重讀，不是憑記憶掃過。抽出其中的決策、約束、偏好、授權、事實陳述，每條填入對帳表：

| # | 原話摘錄 | 類型 | 去向 |
|---|---|---|---|
| 1 | 「single/dual/trio 分別讀…」 | 決策 | `## 介面/資料結構`（dual 表＋single 條目） |
| 2 | 「2.5flash 很便宜可以儘管試」 | 授權 | `## 執行授權` |
| 3 | 「不用做 seed」 | 約束 | `## 非目標` |
| 4 | 「single 先試回灌全文」 | 決策 | 已取代（→ #6） |
| 5 | 「或許之後可以加 fork」 | 延後 | Open Questions #2 |
| 6 | 「改成只回灌最後一集＋摘要」 | 決策 | `## 介面/資料結構` 回灌策略 |

去向只有四種合法值：**spec 條文錨點**（用 spec 的 markdown 標題名稱定位，如 `## 介面/資料結構`，不自創符號——讓使用者能直接搜尋驗證）、**駁回（附理由，且理由已在對話中取得使用者同意）**、**延後（列入 spec 的 Open Questions 段）**、**已取代（→ 對帳表 #N）**。填不出去向的條目就是抓到的遺漏——當場補進 spec。

使用者中途改口是常態不是例外：同一主題多次改口時，以最後一則為準，之前各則標「已取代」並指向取代它的條目——不刪除、不硬塞 spec 錨點。保留改口軌跡的目的，是讓使用者在 Gate 能核對「最終落地的是不是我要的那一版」。

方向必須是對話→spec：從 spec 出發只能驗證「已寫的對不對」，從原文出發才能暴露「沒寫的」。特別規則：使用者對多個平行變體（如 single/dual/trio）給規則時，**每個變體單獨一條**，不得用「其餘自由決定」收攏——被收攏的變體正是最容易無聲消失的。

### 程序二：對稱性檢查

平行成員集合**從使用者意圖與專案文件導出，不是從 spec 自身導出**——對帳表出現過的變體、PRD／SSOT 定義過的成員（多個 workflow、多個角色、多個狀態、多種錯誤分類）都算。從 spec 自身枚舉會漏掉「整個成員在 spec 裡不存在」的情況——而完全消失的成員正是最嚴重的遺漏。

逐成員產出**對稱性矩陣**（成品之一，Gate 呈現）：

| 集合 | 成員 | spec 錨點 | 規格密度 | 判定 |
|---|---|---|---|---|
| workflow | dual | `## 介面/資料結構` 讀寫表 | 完整表格 | ✅ |
| workflow | single | `## 介面/資料結構` 一句話 | 稀疏 | ⚠️ 需追溯（對帳表 #?） |
| workflow | trio | （無） | 缺席 | 遺漏候選 |

成員缺席或密度不對稱時，必須可追溯到使用者的明示決策（對帳表有對應條目）；追溯不到的標為遺漏候選，在 Gate 呈現。判斷「可追溯」時對映的是使用者**意圖**，不是字面——使用者說過「trio 之後再說」就足以解釋 trio 缺席，不需要逐字說過「trio 不寫進 spec」。

### 程序三：具體 trace 走查

挑 1–2 個具體情境（帶具體輸入值，例如「keyword 為 X 的 session，第 2 回合」），沿資料流逐步走完：輸入→每一步處理→輸出；有生命週期的走首輪→第 N 輪。每一步問：「spec 有沒有釘死這裡發生什麼？」

走不下去的那一步就是隱形裁量——你無法在不做決定的情況下把 trace 寫完，所以藏在腦中的決定會被具體情境逼著現形。浮出的決定依影響分流：影響可觀察行為的升為 AC 或寫進介面段；其餘進作者假設清單。這是既有「AC 附範例值」規則的同一原理，擴大到資料流層。

挑選情境時優先：有平行變體時挑會暴露變體差異的路徑、有生命週期時必走非首輪（隱形裁量常藏在「第 2 輪之後」）。走查過程產出**走查紀錄**（成品之一，Gate 呈現）：情境與具體輸入值、逐步資料流、每步的 spec 錨點或「未釘死」標記、浮出的裁量與其分流去向。沒有紀錄的走查視同未執行——這是四道程序中成本最高、最容易被靜默跳過的一道，紀錄就是它的執行證明。

### 程序四：規範句出處（provenance）

隱形決策進 spec 時通常不會寫「由實作決定」——它會直接寫成肯定句（「續回合會回灌完整正文」），字面上看不出這是誰決定的。所以本程序查的不是措辭，是**出處**：對 spec 高影響段落（介面／資料結構、狀態轉移、資料保留、重試與錯誤處理、執行授權）的每一條規範性陳述，逐條問「這條的來源是什麼？」合法出處三種：

- **對帳表 #N**——出自使用者。同程序二的判準：對映意圖而非字面，要判斷的是「這條是不是那句話的忠實轉譯」；轉譯有詮釋空間時，這條同時列入作者假設清單，讓使用者確認詮釋
- **既有 SSOT／ADR**——出自 PRD、TECHSTACK 或既有 spec 的已確認決策，附錨點
- **作者假設**——以上皆非。連同你的預設傾向與影響範圍，集中成**作者假設清單**

顯式的自由措辭（「由實作自行決定」「不限」）同樣要有出處標注（見模板注記）。作者假設清單格式：

| # | 陳述／自由變數 | 我的預設傾向 | 影響 |
|---|---|---|---|
| 1 | 續回合前情回灌內容 | 完整正文全文 | 續回合品質與 continuity |

作者假設不得以陳述句混入正文假裝成共識；清單在 User Review Gate 呈現，由使用者逐項裁決：升為 spec 決策、同意保留為實作自由、或改為其他方案。

## Self-Review B：品質檢查

A 驗「該寫的有沒有寫」，B 驗「已寫的品質」。兩組互補，都要跑：

1. **Placeholder 掃描**：有沒有「TBD」、「待確認」、空白段落？補完或移至 Open Questions
2. **內部一致性**：目標、User Story、驗收條件、Milestones 之間有沒有矛盾？介面設計是否支撐所有驗收條件？
3. **Scope 檢查**：這個範圍適合一個 sprint 嗎？還是需要再拆？
4. **歧義檢查**：有沒有哪個驗收條件能被兩種方式解讀？挑一個寫明確
5. **Reuse Map 完整性**：「既有資產盤點」是否真的盤點過既有 utility / 元件 / 樣式 token？留空、寫「待補」、或顯然沒搜尋就動筆，視為未過——補搜或註明「無，已搜尋 X、Y 確認」
6. **AC 行為性檢查**：每條驗收條件能寫成行為測試（輸入→輸出、render 結果、讀 resolved 值）嗎？寫不成的當場改寫成可觀測行為，或明確標註驗收方式（E2E 截圖、人工驗收）——實作字面 AC 會在開發階段誘發 source-grep 測試
7. **AC 範例值檢查**：關鍵 AC（格式化、計算、排序、邊界值這類輸入→輸出可枚舉者）是否附了具體範例值？枚舉不了的是否改寫成不變量？缺範例的 AC 會迫使 worker 在開發階段自行推導預期值——同一顆腦推導測試與實作，錯會錯得自洽

發現問題直接修正，不需要重跑整個流程。

## User Review Gate

Self-Review A＋B 通過後，向使用者呈現 spec 與四份完整性成品（同一則訊息，spec 為主體、成品附後；過長時可另存檔案並附路徑）：

1. **spec.md**（或其路徑與摘要）
2. **來源側對帳表**——使用者核對的重點不是重讀 spec 全文，而是掃這張表：「我講過的每件事都有去向嗎？表上有沒有少了我記得講過的東西？改口主題的最終版對嗎？」
3. **對稱性矩陣**——缺席與稀疏成員的判定是否符合使用者意圖
4. **走查紀錄**——走不下去的位置是否都已分流
5. **作者假設清單**——逐項裁決：升為決策／同意自由／改方案

> 「Spec 已寫入 `docs/<編號>-<名稱>/spec.md`。附上四份完整性成品：請先掃對帳表確認你講過的都有去向，再看對稱性矩陣與走查紀錄的標記項，最後裁決假設清單各項。確認後可直接進入 `/ddd.work`；需要細化 Milestones 或拆分 sprint 時才進入 `/ddd.tasks`。」

等待使用者回應。使用者要求修改時，只對「修改帶來的變更點」做增量 Self-Review 並同步更新受影響的成品，不整套重跑；以使用者對最新一版的確認為結束條件。假設清單中被裁決的項目，把結論寫回 spec 並更新出處標注為`（使用者已確認）`。

## 產出

- `docs/<編號>-<名稱>/spec.md`
- 來源側對帳表、對稱性矩陣、走查紀錄、作者假設清單（呈現於對話；使用者要求時存檔於文件包）
- Feature branch: `feat/<編號>-<名稱>`

使用者確認規格後，引導使用者執行 `/ddd.work`；需要細化 Milestones 或拆分 sprint 時，才引導 `/ddd.tasks`。
